# Sonasphere — архитектура

Статус: черновик v0, 2026-10-31. Решения из §3 приняты; открытые вопросы собраны в §10.

## 1. Что это и где границы

Sonasphere — среда для live coding музыки в духе Sonic Pi, Strudel и TidalCycles. Интерфейс — CLI:
REPL или исполнение файла `.sona`. GUI не планируется, TUI — когда-нибудь потом.

Система состоит из двух программ, которые связывает только поток команд:

|            | **sona**                                              | **bitvm**                                                |
|------------|-------------------------------------------------------|----------------------------------------------------------|
| Отвечает за | музыкальную мысль: язык, паттерны, темп, композицию, эргономику автора | звук, точное время, DSP-вычисления          |
| Знает      | синтаксис `.sona`, доли и такты, имена сэмплов, инструменты как описания | абсолютное время, сэмпл-фреймы, буферы, узлы, шины, аудиодрайвер |
| Не знает   | ALSA, аудиобуферы, RT-потоки, устройство DSP-юнитов   | грамматику sona, ключевые слова, файлы скриптов, темп и такты |
| Процесс    | `sona` — REPL и исполнитель файлов                    | `bitvmd` — демон                                         |

Общее у них одно — **протокол bitvm** (`shared/`): атомарные команды с временными метками. Это ISA
виртуальной машины bitvm, а sona — компилятор из музыкального языка в этот ISA.

## 2. Общая схема

```
        sona (процесс)                                bitvmd (процесс)
┌──────────────────────────────────┐        ┌────────────────────────────────────────┐
│ REPL-строка / файл .sona         │        │ control thread                         │
│  ↓ lang     парсер, вычислитель  │        │  сокет → декодер → валидация           │
│  ↓ session  треки, инструменты   │        │  GraphDef, буферы (файлы — в worker)   │
│  ↓ sched    темп, lookahead      │ бандлы │  экземпляры узлов: вся аллокация здесь │
│  ↓ lower    события → команды    │ ─────▶ │   ↓ SPSC                               │
│  ↓ client   ID, зеркало ресурсов │ ◀───── │ audio thread (RT)                      │
│             кодек (shared/)      │ ответы │  очередь по времени → узлы → шины      │
└──────────────────────────────────┘        │   ↓                                    │
                                            │ backend: ALSA | offline (WAV)          │
                                            └────────────────────────────────────────┘
```

Путь одной ноты: строка в REPL → вычислитель обновляет паттерн трека → планировщик за ~150 мс до
нужного момента запрашивает события → `lower` превращает событие в `node.new` с меткой времени →
бандл уходит в bitvmd → control thread заранее создаёт экземпляр графа → audio thread включает его
ровно в нужный сэмпл.

## 3. Принятые решения

| #   | Решение | Почему | Отвергнуто |
|-----|---------|--------|------------|
| D1  | Два процесса: `bitvmd` (демон) и `sona` (клиент) через Unix-сокет | падение или перезапуск REPL не рвёт звук; граница физическая; можно подключить несколько клиентов. Так устроены SuperCollider и Tidal/SuperDirt | один процесс; оба режима |
| D2  | Свой бинарный протокол плюс текстовая форма (asm/disasm) | типизация, компактность, дешёвое декодирование; текст — для логов, ручной отладки и golden-тестов | OSC |
| D3  | bitvm с первого дня исполняет DSP-графы (GraphDef) | инструменты и эффекты описываются в sona, и bitvm не приходится расширять под каждый новый звук | фиксированный набор инструментов |
| D4  | Абстракция `AudioBackend`; первые реализации — ALSA и offline | ALSA работает и на голом железе, и через pipewire-alsa; offline даёт детерминированные тесты | JACK, miniaudio |
| D5  | bitvm знает только абсолютное время: `CLOCK_MONOTONIC`, наносекунды, `int64` | темп и такты — музыкальная мысль, им место в sona | общая шкала долей |
| D6  | sona планирует с упреждением (lookahead), bitvm исполняет точно в срок | джиттер IPC и время вычисления языка не влияют на ритм | отправка событий «прямо сейчас» |
| D7  | Вся аллокация — в control thread; audio thread только подключает готовое | RT-безопасность без собственного RT-аллокатора | RT-аллокатор, как в scsynth |
| D8  | Узлы связываются только через шины | простая модель; порядок исполнения задаёт дерево групп | прямые связи между узлами |
| D9  | ID объектов выделяет клиент в диапазоне, который выдал сервер | бандл с новым узлом уходит без round-trip | ID от сервера |
| D10 | Многоканальность раскрывает sona при построении графа | bitvm видит только моно-провода и остаётся простым | многоканальные провода в bitvm |
| D11 | C++23, meson, gtest | GCC 16 и Clang 23 поддерживают C++23 целиком; gtest уже стоит в системе | doctest, Catch2 |

## 4. Протокол (`shared/`)

Полная спецификация появится в `docs/protocol.md` на этапе M1. Здесь — каркас.

### Транспорт

- `AF_UNIX` + `SOCK_SEQPACKET`: доставка надёжная и по порядку, границы сообщений сохраняются,
  сервер видит отключение клиента.
- Путь: `$XDG_RUNTIME_DIR/sonasphere/bitvm.sock`. Каталог с правами 0700 даёт доступ только
  текущему пользователю. Для нескольких экземпляров у сервера есть имя: `bitvm-<name>.sock`.
- Одно сообщение — один пакет. Предел размера пакета фиксируется в M1; длинные бандлы дробятся.

### Сообщение

```
Header:  magic u32 | version u16 | kind u16 | seq u32 | payload_len u32
kind:    HELLO | BUNDLE | REQUEST | REPLY | NOTIFY
команда: opcode u16 | len u16 | поля
```

- Порядок байт little-endian, поля фиксированной ширины, строки — `u16` длина + байты UTF-8.
- По длине команды декодер пропускает незнакомые опкоды и проверяет границы.
- Хендшейк: клиент шлёт `HELLO` (версия протокола, имя клиента). Сервер отвечает версией,
  `client_id`, диапазоном ID, частотой дискретизации, размером блока, числом шин и задержкой вывода.
  По задержке sona выбирает минимальный lookahead.

### Бандл

`BUNDLE(time_ns, [команды…])` — основная единица. Все команды бандла исполняются атомарно на одном
сэмпл-фрейме. `time_ns = 0` значит «как можно скорее». При равном времени сохраняется порядок
прибытия.

### Классы команд

| Класс | Где исполняется | Когда | Примеры |
|-------|-----------------|-------|---------|
| RT-команды | audio thread | по метке бандла | `node.new`, `group.new`, `node.free`, `node.set`, `node.run`, `node.move`, `group.clear`, `cbus.set` |
| Ресурсные | control thread / worker | сразу при получении; ответ `DONE` или `FAIL` с `seq` | `def.load`, `def.free`, `buf.load`, `buf.alloc`, `buf.free` |
| Запросы | control thread | сразу; ответ `REPLY` с `seq` | `status`, `sync` (ответ после обработки всего, что пришло раньше), `hush` |
| Уведомления сервер → клиент | — | — | `n_end`, `late`, `xrun`, `done`, `fail`; позже — уровни сигнала |

Ресурсные команды не попадают в бандлы с меткой времени. Клиент ждёт `DONE`, прежде чем планировать
узлы, которым нужен ресурс.

### Текстовая форма

Взаимно однозначна с бинарной, одна команда на строку. Набросок (синтаксис фиксируется в M1):

```
def.load id=12 file=pluck.bvg
@+0.250 node.new id=1001 def=12 add=tail target=10 freq=440 amp=0.2
@+0.500 node.set id=1001 gate=0
```

Где пригодится: `bitvmd --trace`, `bitvmctl` (ручная отправка команд), golden-тесты sona, файлы
партитур для offline-рендера.

## 5. bitvm

### Объектная модель

Модель взята у scsynth, она проверена временем.

- **GraphDef** — описание DSP-графа: инструмента или эффекта. Загружается один раз, экземпляров —
  сколько угодно.
- **Node** — экземпляр GraphDef в дереве исполнения: звучащая нота или эффект на шине.
- **Group** — узел-контейнер, задаёт порядок исполнения. Корень дерева — группа 0.
- **Bus** — аудиошина (блок сэмплов) или контрольная шина (одно значение). Первые N аудиошин —
  выходы звуковой карты.
- **Buffer** — массив сэмплов в памяти: загруженный файл или выделенная область.

Узлы исполняются при обходе дерева в глубину. Источники стоят раньше эффектов, которые читают их шины.
Встроенных инструментов в bitvm нет: стандартные инструменты лежат в `stdlib/` на языке sona и
загружаются при старте как GraphDef.

### GraphDef — то, что делает bitvm виртуальной машиной

- **Параметры:** имя, значение по умолчанию, rate. На проводе параметр адресуется индексом, имена
  нужны для текстовой формы и отладки.
- **Константы:** таблица значений.
- **Юниты** в топологическом порядке. У каждого есть тип (имя из каталога bitvm), rate (`audio` —
  каждый сэмпл, `control` — раз в блок, `init` — раз при создании узла), входы и число выходов. Вход
  ссылается на константу, на параметр или на выход ранее объявленного юнита.
- **Циклов нет.** Обратная связь идёт через шины (с задержкой в блок) или через явные юниты задержки.
- **Каталог юнитов** фиксирован в bitvm: осцилляторы, шум, огибающие, фильтры, задержки, ревер,
  сэмплер, панорама, арифметика, `In`/`Out` для шин. При загрузке имена превращаются в указатели на
  функции, так что в RT уже нет поиска по строкам.
- **Загрузка** = валидация (типы, rates, ссылки, топология, известные юниты) + расчёт раскладки памяти
  экземпляра. Невалидный граф отклоняется с `FAIL`. bitvm не должен падать ни на каком входе.

### Исполнение

- Внутренний блок — 64 фрейма (≈1,3 мс при 48 кГц), независимо от периода бэкенда: период ALSA
  рендерится несколькими блоками.
- Узел стартует и останавливается с точностью до сэмпла (смещение внутри блока). `node.set`
  применяется на границе блока; при необходимости уточним позже.
- Когда юнит с done-флагом заканчивается (огибающая отзвучала), узел освобождает себя сам, и клиенту
  уходит `n_end`.
- Параметры меняются с линейным ramp, чтобы эффекты в лайве двигались плавно.

### Потоки и RT-правила

1. **audio thread** (`SCHED_FIFO`, если система разрешает). Забирает готовые команды из SPSC в
   очередь по времени (heap с заранее выделенной ёмкостью), рендерит блоки, исполняет события в
   нужный фрейм.
   Запрещено: выделять и освобождать память, брать мьютексы, делать файловый и сетевой ввод-вывод,
   бросать исключения, логировать (кроме lock-free кольца), крутить циклы, длина которых зависит от
   ввода клиента и ничем не ограничена.
2. **control thread.** Сокеты (io_uring / epoll), декодирование, валидация, ответы клиентам. Здесь создаются
   экземпляры узлов: бандлы приходят заранее, на величину lookahead, и времени на аллокацию хватает.
3. **worker.** Читает файлы сэмплов через libsndfile, чтобы не блокировать control thread.

Дополнительно:

- Обратный SPSC (RT → control) везёт объекты на удаление и уведомления (`n_end`, `late`, `xrun`).
- Таблицы «ID → объект» на RT-стороне — открытая адресация с фиксированной ёмкостью, без аллокаций.
- Узлы не держат указатель на Buffer дольше одного блока, поэтому `buf.free` безопасен в любой момент.
- В debug-сборке `operator new`/`malloc` перехватываются и падают при вызове из audio thread.

### Время

- Метка бандла — момент, когда звук должен прозвучать на выходе, с учётом задержки устройства.
- `TimeMap` сопоставляет фрейм и `CLOCK_MONOTONIC`. Соответствие сглаживается DLL по наблюдениям
  бэкенда (`snd_pcm_delay`, htimestamp). Смещение события в блоке = (t − t_блока) · sr.
- Опоздавшее событие исполняется в ближайший фрейм и попадает в счётчик. Клиенту уходит `late`, и
  sona может увеличить lookahead.
- В offline-режиме время виртуальное (фрейм / sr от нуля), рендер идёт быстрее реального. Отсюда
  детерминированные тесты и рендер партитур в WAV.

### Бэкенды

`AudioBackend`: `open(config)` возвращает фактические sr, период и число каналов; `start(callback)`
работает по pull-модели — бэкенд в своём потоке вызывает `engine.process(out, frames, time)`; `stop()`.

- **ALSA** — свой поток, `snd_pcm_writei` или mmap, восстановление после xrun с уведомлением.
- **Offline** — пишет в WAV или в буфер памяти для тестов.
- Позже: JACK, нативный PipeWire, захват входа.

### Жизнь демона

- Отключение клиента не останавливает звук — ради этого и нужны два процесса. Опция
  `--free-on-disconnect` меняет поведение.
- При старте sona ищет сокет и, если bitvmd не запущен, поднимает его сама. Флаг `--no-spawn` это
  отключает.

## 6. sona

### Конвейер

```
текст → lang      лексер, парсер, AST, вычислитель
      → session   именованные сущности: треки, паттерны, инструменты, эффекты
      → sched     часы; каждые ~10–20 мс запрашивает у активных треков события в окне [горизонт, now + lookahead)
      → lower     событие → бандлы с node.new / node.set; инструмент → GraphDef
      → client    соединение, хендшейк, выделение ID, зеркало ресурсов, ответы сервера
```

### Модули

- **lang** — грамматика sona. Проектируется отдельно (сессия L1).
- **pattern** — семантическая модель музыкального времени. Ключевой интерфейс не зависит от
  синтаксиса: «дай события в интервале [a, b)». Он подходит и для циклических паттернов
  (Tidal/Strudel), и для императивных циклов со `sleep` (Sonic Pi — через виртуальное время и корутины).
- **graph** — типизированный C++ API для построения GraphDef из юнитов. Его вызывают вычислитель
  языка, stdlib и тесты.
- **session** — состояние REPL. Хранит исходный текст каждого определения, поэтому `save` выгружает
  сессию в декларативный `.sona`-файл, а `load` исполняет файл в сессию. REPL и файлы — одна модель.
- **sched** — часы: темп и якорь (доля b0 в момент t0). Смена темпа ставит новый якорь с будущей
  доли, поэтому ритм не дёргается. Lookahead по умолчанию 100–200 мс и настраивается.
- **lower** — превращает музыкальные события в команды bitvm. Это единственное место, которое знает
  семантику протокола.
- **client** — транспорт, аллокатор ID в выданном диапазоне и зеркало того, что загружено в bitvm
  (defs, буферы, группы, эффекты). Если bitvmd перезапустить, sona восстановит всё сама.
- **repl** — редактирование строки, история, мета-команды.

### Потоки и данные

- REPL-поток вычисляет код, поток планировщика генерирует события. Мьютексов между ними нет: трек
  хранит `std::atomic<std::shared_ptr<const Pattern>>`, REPL публикует новую неизменяемую версию,
  а планировщик на каждом тике берёт снимок.
- Новый паттерн вступает в силу с ближайшей границы квантования (доля, цикл или такт), а не мгновенно.
- Сэмплы: sona резолвит имена (`bd:3`) в пути по библиотекам сэмплов из конфига и шлёт `buf.load`
  с путём. Процессы живут на одном хосте, так что путь валиден и для bitvmd.

### Режимы запуска

- `sona` — REPL.
- `sona file.sona` — исполнить композицию. С `--watch` файл перечитывается при каждом сохранении:
  live coding из любого редактора.
- `sona --render out.wav file.sona` (позже) — sona пишет партитуру (поток бандлов), bitvm рендерит её
  offline.

## 7. Репозиторий и сборка

```
meson.build, meson.options   корень: опции, флаги предупреждений, общие зависимости
shared/                      протокол bitvm: команды, кодек, текстовая форма, транспорт
  include/bitvm/proto/
bitvm/                       движок
  include/bitvm/             API движка для bitvmd, утилит и тестов
  src/                       engine, graph, dsp, backend, io, server
  bitvmd/                    демон
  tools/                     bitvmctl и другие утилиты; видят только shared/
sona/
  include/sona/              API libsona для приложения и тестов
  src/                       lang, pattern, graph, session, sched, lower, client, repl
  app/                       исполняемый sona
stdlib/                      стандартная библиотека на языке sona: инструменты, эффекты, гаммы
examples/                    примеры .sona
docs/                        архитектура и спецификации
```

Границу проверяет сборка: цели sona зависят только от `bitvm_proto_dep`, include-каталоги движка
sona не видит, и `#include <bitvm/engine.hpp>` внутри sona просто не скомпилируется.

Зависимости: alsa-lib (опция `alsa`), libsndfile (опция `sndfile`), gtest (опция `tests`), pthreads.
Библиотека редактирования строки для REPL пока не выбрана (§10).

Пока в компоненте нет ни одного `.cpp`, его библиотека объявлена как `declare_dependency` с одними
заголовками. С первым исходником она становится `static_library`: meson больше не разрешает
библиотеки без исходников.

## 8. Тестирование

- **shared:** roundtrip «бинарь ↔ структуры ↔ текст»; фаззинг декодера (libFuzzer, clang).
- **bitvm:** тесты отдельных юнитов; offline-рендер партитур с проверкой точности (онсет ровно в
  ожидаемом фрейме); валидатор GraphDef на испорченных входах; RT-guard в debug.
- **sona:** парсер; golden-тесты «программа + окно времени → текстовый поток команд».
- **Сквозной:** sona → партитура → bitvm offline → WAV.

## 9. Дорожная карта

Одна сессия — один этап.

| #  | Этап | Зависит от | Готово, когда |

| M1 | **shared:** протокол v0 — заголовок, команды, бинарный кодек, текстовая форма, транспорт SEQPACKET | — | roundtrip-тесты зелёные, `docs/protocol.md` написан |

L1 можно начать хоть сейчас — он не требует кода.

## 10. Открытые вопросы

Язык (сессия L1):

1. Музыкальное время: циклы (Tidal/Strudel, cps), доли и такты (BPM, размер) или циклы поверх долей?
2. Семантика: декларативные паттерны, императивные циклы со `sleep` или гибрид?
3. Как в REPL именуются и переопределяются сущности, как квантуется подмена.
4. Синтаксис описания инструментов (DSP-графов) и эффектов.
5. Маршрутизация эффектов: цепочки на трек (`with_fx` в Sonic Pi) или общие шины (orbits в Tidal)?
6. Мета-команды REPL — часть языка или отдельный слой (`:load`, `:save`)?
7. Раскладка библиотек сэмплов и схема имён (`bd:3`, как в Dirt-Samples?).

Техника:

8. Редактор строки для REPL: libedit, readline (GPL), replxx или isocline. Для будущего TUI — FTXUI
   или notcurses.
9. Схема ID при нескольких клиентах: предложение — диапазон на клиента; уточнить в M1.
10. Нужен ли захват звука (вход) в первой версии.
11. Ramp параметров: только линейный или ещё экспоненциальный.
