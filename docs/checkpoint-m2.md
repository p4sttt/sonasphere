# Чекпоинт M2

Дата: 2026-11-04. Контекст восстановлен из `CLAUDE.md`, архитектуры, спецификации и журналов
Claude Code в `~/.claude/projects/-home-d4y2k-src-sonasphere/`.

## Что реализовано

- M1: проверка неизвестных `Rate` и `InputSource` в публичном API; устранение переполнения индексов
  констант при разборе больших текстовых графов; неблокирующая проверка занятого Unix-сокета,
  включая заполненную очередь подключений. Каждая ошибка воспроизведена регрессионным тестом.
- M2: загрузка и компиляция GraphDef, все девять юнитов каталога v0, IR/KR/AR, линейные ramps,
  огибающие с done и retrigger, пауза, аудио- и контрольные шины.
- Дерево с фиксированной таблицей ID, итеративными обходами и удалением; все RT-команды, мягкие
  пропуски и runtime-откат созданных узлов. Уже выполненные не создающие команды сохраняются.
- Ограниченные SPSC и heap, стабильное расписание по исходному времени, целочисленный TimeMap,
  политика опоздания, POD-уведомления, отложенное уничтожение на control-стороне.
- Ресурсы с детерминированными номерами: GraphDef, диапазоны шин, буферы; синхронный `buf.load`
  для offline при включённом libsndfile. Граф удерживается подготовленными и активными синтами
  после `def.free`; повторная загрузка не переиспользует номер.
- Партитуры `.bvs` и `.bvsb`, контекст имён параметров, относительные пути графов/сэмплов, точные
  границы callback, выход в память и float32 WAV, утилита `bitvm-render` и пример трёх нот.

## Границы абстракций

| Модуль | Ответственность |
|--------|-----------------|
| `shared/` | данные протокола, кодеки, валидация, каталог, транспорт |
| `CompiledGraph` | проверка графа, разрешённые инструкции, раскладка памяти |
| `GraphInstance` | состояние одного синта и вычисление одного активного фрейма |
| `Buses` | память сигналов и поколение аудиоблока |
| `NodeTree` | поиск ID, порядок исполнения, проверка циклов, операции над поддеревьями |
| `Engine` | подготовка бандлов, планирование, исполнение, граница control/audio |
| `TimeMap` | перевод наносекунд в фреймы без раннего исполнения |
| `Score` / offline-driver | порядок сообщений, виртуальное время, ошибки партитуры |
| `AudioBackend` / `OfflineBackend` | формат и вывод готовых сэмплов вне RT |

Кодек не получил искусственную иерархию классов: общая модель `Message` уже разделяет бинарное и
текстовое представления. Нет зависимостей sona от движка или движка от языка sona.

## Дополнительные ошибки, найденные ревью

- Порядок разных временных меток, попавших в один сэмпл, сохраняется по времени.
- `client.reset` отменяет будущие бандлы и сразу возвращает их резерв памяти и очереди.
- Клиент 255 не может освободить зарезервированные выходные аудиошины.
- Успешный `sync` не выдаётся, пока не применены предыдущие немедленные бандлы.
- Длительность `0.07` при 48 кГц даёт 3360 фреймов; дробные фреймы округляются вверх после
  приведения длительности к наносекундной точности протокола.
- Скобки в допустимом имени файла графа не нарушают разбор партитуры.
- Ошибки формата сэмпла отличаются от ошибок файлового ввода-вывода.
- Параметры как KR-источники постоянны внутри блока, включая чтение AR-юнитами. Возобновление
  синта после пропущенной границы блока обновляет KR-снимки и не продвигает огибающие за паузу.
- Переполнение уведомлений в offline приводит к явной ошибке; возможная потеря ошибки бандла
  не превращается в успешный результат рендера.

## Как запустить

```bash
meson compile -C build
build/bitvm/bitvm-render --duration 2 examples/offline/ping.bvs build/sonasphere-m2.wav
meson test -C build --print-errorlogs
meson test -C build-asan --print-errorlogs
meson test -C build-fuzz --suite fuzz --print-errorlogs
```

Для полного набора тестов нужны локальные Unix-сокеты и возможность LeakSanitizer проверять
процесс; ограничения sandbox могут блокировать эти операции. Это проверяется отдельно от ошибок кода.

## Результаты проверки

| Проверка | Результат |
|----------|-----------|
| Обычная сборка GCC, `meson test -C build --no-rebuild --print-errorlogs` | 15/15 целей, 188/188 gtest |
| GCC ASan/UBSan и LeakSanitizer, полный набор | 15/15 целей, 188/188 gtest; без диагностик |
| Clang/libFuzzer + ASan/UBSan, декодер и текст | 2/2, по 20 000 запусков |
| Без ALSA, libsndfile, gtest (`build-minimal`) | сборка проходит |
| Форматирование новых файлов C++, `git diff --check` | проходят |
| Пример `ping.bvs`, два независимых рендера | одинаковые WAV, 48 кГц, стерео, 96 000 фреймов |

Пример находится в `build/sonasphere-m2.wav` (каталог сборки игнорируется Git).
SHA-256: `91408ba660eac992b1448ebc342b0d5428795a6dc31d8ef6b70c88afb15b6a22`.
Положение начала и конца нот дополнительно проверяется по отдельным фреймам в `core` и `offline`.
В RT-тесте создание, done, откат и удаление не вызывают аллокаций или освобождения памяти.

## Следующий этап

M3: настоящий `bitvmd`, соединения и хендшейк, подписки и счётчики по клиентам, асинхронные fences
для `sync`/запросов состояния, realtime-driver ALSA, согласование формата и часов устройства,
RT-приоритет, xrun и `bitvmctl`.

В M2 `call`, `tree`, `status` требуют остановленного callback. Если немедленный бандл ещё ждёт
следующей границы блока, `call(Sync)` возвращает `context`: нужно дорендерить до границы и повторить.
Offline-driver применяет бандл перед следующим CALL. В M3 ожидание должно стать асинхронным.

Синтаксис sona остаётся отдельным этапом L1; `sona` и `bitvmd` пока каркасы. Коммитов и публикаций
в этой работе нет; исходные незакоммиченные изменения M1 сохранены.
